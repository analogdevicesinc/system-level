ADSP SoC Clock Architecture
===========================

The ADSP clock architecture is made up of a few core hardware blocks that are responsible for generating and routing core system clocks
throughout the SoC. The exact clock trees between SoCs can vary however they share a common structure between them, allowing
customers to configure system clocks to their specific needs.

Clock Generation Unit (CGU)
---------------------------

The CGU is responsible for generating all core system clocks used throughout the ADSP SoCs, it is made up of various core parts such as the PLL
(phased-locked loops), divider clocks and clock gating control. The ADSP SoCs have two CGU blocks, CGU0 and CGU1. By default core system peripherals
are clocked via CGU0 (the default CGU) and CGU1 can be used to further configure and customise how peripherals are clocked across the SoC.

The following diagram shows the high level clock generation path used by ADSP SoCs. Both CGUs are fed by a ``SYS_CLKINx``
reference clock, which operates at a fixed frequency of ``25 MHz``. Each CGU PLL uses the reference clock to generate a PLL clock
output (``PLLCLK``), which is then routed through upstream dividers to produce the core system clocks required by the SoC.

.. note::

   - The ``CLKINSEL`` mux selects either ``SYS_CLKIN0`` or ``SYS_CLKIN1`` as the reference clock for CGU1.
   - The ADSP-SC846 SoC does not have a ``CLKINSEL`` mux, both CGUs use ``SYS_CLKIN0`` by default.
   - The ADSP-SC598 has a specialised PLL block which clocks the DDR memory controller, this allows
     DDR to be clocked via the CDU or via the PLLs ``DCLK`` clock.

Each CGU can be configured independently, allowing different groups of system clocks to operate at different frequencies.
The divider stage determines the frequency of each generated clock output, while clock gating controls whether individual
clocks are enabled or disabled.

The CGU is responsible for generating these clock sources. Selection and routing of the generated clocks to core peripherals such as
processors, memory controllers, ethernet etc. is handled separately by the Clock Distribution Unit (CDU).


Clock Distribution Unit (CDU)
-----------------------------

The Clock Distribution Unit (CDU) selects and routes clocks generated by the CGUs to core SoC peripherals. Each CDU output (``CLKO[n]``) contains a
multiplexer that selects one of up to four possible input clocks, along with clock gating functionality used to enable or disable the output. Each
``CLKO[n]`` is connected to a fixed SoC target and has a predefined set of possible parent/input clocks.

The number of configurable CDU outputs varies between ADSP SoCs. The ADSP-SC573, ADSP-SC589, ADSP-SC594, ADSP-SC598 and ADSP-SC846 provide 8, 10, 12, 14 and 14 
configurable CDU outputs respectively.

   valid clock source and must not be selected. Clocks or outputs marked ``Reserved`` are reserved for internal
   processor use and must not be configured by software.

Initial U-Boot clock configuration
-----------------------------------

The initial ADSP clock configuration is programmed by U-Boot during early system initialisation before Linux has started. U-Boot configures the CDU followed by the
CGU during this phase. The CDU initialisation selects the reference clock used by CGU1 and programs the initial input clock selection and enable state for each
supported ``CLKO[n]`` CDU output.

The CGU initialisation configures CGU0 and CGU1 using the SoC specific clock settings, including the PLL multiplier, input divider, and system clock
divisors, etc. The PLL is placed into bypass mode while the new configuration is programmed and is then returned to normal operation once the clock settings
have been applied.

After Linux starts, the ADSP clock drivers register the CGU and CDU clocks with the the `Linux common clock framework <https://docs.kernel.org/driver-api/clk.html>`_.

Peripheral drivers can then obtain and manage their required clocks through the Linux common clock framework APIs. Drivers can request operations such as enabling or
disabling a clock, changing its rate, or selecting a parent clock where supported. These requests are handled by the corresponding ADSP clock provider, which performs
the required hardware configuration. For CDU output clocks for example, these requests are translated by the CDU clock driver into the corresponding clock mux
and gate operations.

------------------

The ADSP Linux clock implementation consists of shared clock drivers and

To find the latest ADSP clock drivers navigate to ``drivers/clk/adi`` in the ADI Linux kernel repository. See :ref:`Linux support <adsp linux-support>`
for the current ADSP Linux development and release branches.

.. note::

   ADSP Linux clock support is under active development, and feature coverage
   may vary between SoCs.

Debugging ADSP clocks
-----------------------

Linux provides several ``debugfs`` interfaces that can be used to inspect the
ADSP clock configuration. The `Linux common clock framework
<https://docs.kernel.org/driver-api/clk.html>`_ provides a summary of the Linux
clock topology, while the ADSP CDU driver provides access to the current CDU
hardware register state.

CCF clock summary
^^^^^^^^^^^^^^^^^

The Linux common clock framework exposes ``clk_summary`` through ``debugfs``.
This provides an overview of the clocks registered with Linux, including their
parent relationships, enable states, and current clock rates.

To view the clock summary:

.. code-block:: console

   $ cat /sys/kernel/debug/clk/clk_summary

Example output:

.. code-block:: text

    cgu0_cdiv         1       1        0        1000000000  0          0     50000      Y                  deviceless                      no_connection_id
      cclk0_0         1       1        0        1000000000  0          0     50000      Y                    deviceless                     no_connection_id
        cdu_sharc0    1       1        0        1000000000  0          0     50000      Y                       deviceless                    no_connection_id

The example above shows ``cdu_sharc0`` derived from its parent clock ``cclk0_0``, which is in turn derived from the divider clock ``cgu0_cdiv``.
The indentation reflects the parent child relationship between the clocks.

The output can be used to verify the clock hierarchy and confirm the rate and enable state of clocks managed by the ADSP clock drivers.

CDU register dump
^^^^^^^^^^^^^^^^^

The ADSP CDU driver exposes a register dump through ``debugfs`` for
CDU specific clock debugging. The dump provides the live CDU register state,
including input clock selection, output enable state, and CDU status
information.

To view the CDU register dump:

.. code-block:: console

   $ cat /sys/kernel/debug/clk/cdu_sharc0/cdu_cfg[0]

Example output:

.. code-block:: text

   CDU_CFG[0]: 0x00000001
     EN:   1
     SEL:  0
     LOCK: 0
   CDU_STAT: 0x00000000
     LWERR:  0
     ADRERR: 0
     CLKO0:  0


The example above shows the ``CLKO0`` CDU output enabled with input clock ``IN0_CLKO0`` selected. The CDU output is not locked, and ``CLKO0`` shows that the CDU output 
is not currently undergoing a configuration change. ``LWERR`` and ``ADRERR`` are both clear, indicating that no lock write or invalid address errors have been reported.

The ``clk_summary`` output shows the clock topology as registered with the Linux common clock framework, while the CDU register dump provides the
corresponding hardware configuration state. Using both interfaces can help identify differences between the clock configuration expected by Linux and
the current CDU hardware state.
